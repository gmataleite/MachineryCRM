# ADR-003: Central Database: PostgreSQL with PostGIS and pgvector

## Status
Accepted

## Date
2026-09-03

## Context
MachineryCRM relies on highly structured relational data (Clients, Machines, Maintenance, Communications) requiring strict ACID compliance. Additionally, the system has two specialized data processing requirements: 
1. Geospatial querying to support the mapping and routing modules (e.g., identifying machines within a specific radius of a technician).
2. Vector similarity search to support the Natural Language (Text-to-SQL) AI module, which requires embedding storage and semantic indexing.
Relying on separate infrastructure for each requirement (a relational DB, a spatial engine, and a standalone vector DB) would introduce extreme operational overhead and data synchronization risks.

## Decision
Adopt **PostgreSQL** as the central relational database system, explicitly utilizing the **PostGIS** extension for geospatial capabilities and the **pgvector** extension for AI embedding storage and vector operations.

## Rationale
*   **Infrastructure Consolidation:** PostgreSQL natively supports specialized extensions, allowing relational, spatial, and vector workloads to coexist within the same database engine and transaction scope. This eliminates the need to maintain distributed state across multiple database technologies.
*   **PostGIS:** It is the industry standard for geospatial data processing. It allows the backend to offload complex geographic calculations (bounding boxes, radius searches, distance calculations) directly to the database layer, executing them with highly optimized spatial indexes (GiST).
*   **pgvector:** It enables the storage of vector embeddings generated by the LLM and performs exact and approximate nearest neighbor search (HNSW/IVFFlat). This allows the Text-to-SQL Python microservice to leverage semantic context directly from the primary datastore.
*   **Tooling Alignment:** Entity Framework Core (the chosen .NET ORM) provides robust, official support for PostgreSQL, including native translation of LINQ queries to PostGIS spatial functions.

## Consequences

### Positive
*   Single source of truth for all business, geographical, and AI-related data.
*   Simplified deployment topology and reduced infrastructure costs compared to provisioning three distinct database systems.
*   Full ACID compliance across standard and specialized data types.

### Negative
*   Increases the complexity of local development setup and CI/CD pipelines, as the Docker images must be custom-built or carefully selected to include both PostGIS and pgvector concurrently.
*   Geospatial and vector indexes have distinct memory and compute profiles; performance tuning (e.g., configuring `work_mem` and `shared_buffers`) will require active monitoring as the dataset grows.
